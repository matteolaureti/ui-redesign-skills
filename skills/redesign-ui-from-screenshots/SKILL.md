# UI Screenshot Redesign Skill

## Purpose

Use this skill when the user provides one or more screenshots of an existing interface and asks to:

- redesign it
- modernize it
- improve its UI
- explore alternative layouts
- make it more professional
- make it feel more premium
- remove generic or AI-generated aesthetics
- create multiple visual directions
- rethink a dashboard, SaaS interface, web app, landing page, website, mobile UI, pricing page, settings page, onboarding flow, card, modal, navigation, or individual section

The goal is **not to reproduce the screenshot with different colors**.

The goal is to understand what the existing interface is trying to accomplish and then produce a significantly stronger visual solution.

---

# Core Principle

Treat the input screenshot as a:

**functional reference, content reference, and product-context reference**

—not as a layout template that must be copied.

Preserve what the interface needs to communicate.

Feel free to radically redesign how it communicates it.

Unless the user explicitly asks for a light restyle, you may change:

- overall page composition
- navigation architecture
- information hierarchy
- grid
- alignment
- card structure
- grouping
- spacing
- typography
- surface treatment
- visual density
- component shape
- section order when UX meaning is preserved
- presentation of metrics
- presentation of filters
- tables
- charts
- settings
- forms
- empty areas
- contextual actions
- decorative elements

A redesign should feel like the same product designed by a significantly better product design team.

---

# 1. Understand the Screenshot Before Redesigning

Before generating anything, visually inspect the supplied screenshot.

Determine:

## Product type

Identify whether this is primarily:

- SaaS dashboard
- admin panel
- analytics interface
- CRM
- content management tool
- marketplace
- e-commerce interface
- fintech product
- developer tool
- AI product
- landing page
- marketing website
- onboarding
- settings
- billing
- account management
- mobile application
- other product UI

## Primary user goal

Identify the main action or information the page exists to support.

Examples:

- monitor performance
- configure something
- manage accounts
- compare plans
- create content
- inspect data
- manage devices
- perform onboarding
- review activity
- complete a purchase
- understand product value

This goal must remain obvious in the redesign.

## Information architecture

Identify:

- primary navigation
- secondary navigation
- page title
- key actions
- main data
- supporting data
- controls
- cards
- lists
- tables
- charts
- forms
- filters
- status indicators
- contextual actions
- warnings
- help information

Distinguish **essential information** from visual noise.

---

# 2. Preserve Product Meaning

Unless explicitly asked to rethink UX or functionality, preserve the underlying meaning of the existing UI.

Do not accidentally remove an important capability simply because it makes the screenshot cleaner.

Keep recognizable equivalents of:

- critical actions
- statuses
- metrics
- filters
- controls
- navigation
- selected items
- plan information
- account information
- device information
- warnings
- progress
- relevant metadata

However, these elements do **not** need to retain their original visual form.

For example, a group of five bordered statistic cards could become:

- one consolidated summary surface
- inline metrics
- a horizontal data strip
- contextual values integrated into a header
- a visual analytics module

Preserve the information, not necessarily the component.

---

# 3. Do Not Be Overly Loyal to the Original Layout

One of the biggest failures in screenshot redesign is producing:

> the same page with slightly nicer cards.

Avoid this.

If the existing composition is weak, rebuild it.

You may:

- merge redundant cards
- remove unnecessary containers
- convert card grids into structured surfaces
- replace left sidebars with top navigation
- introduce secondary rails
- use asymmetric layouts
- create split layouts
- move actions closer to the content they affect
- consolidate scattered metadata
- create stronger visual focal points
- move secondary information into lower-emphasis regions
- replace grids with lists
- replace lists with visual timelines
- replace separate widgets with integrated modules
- use tabs instead of showing everything simultaneously
- create progressive disclosure

The redesign should prioritize usability and visual hierarchy rather than fidelity to the old layout.

---

# 4. Visual Audit

Evaluate the screenshot for the following problems before redesigning it.

## Typography

Watch for:

- generic typography
- Inter used without deliberate typographic treatment
- weak hierarchy
- headings too similar to body text
- oversized headings that waste dashboard space
- excessive bold text
- only Regular and Bold weights
- poor line-height
- weak contrast between labels and values
- all-uppercase labels everywhere
- poor number alignment
- cramped text
- inconsistent sizes
- excessive tiny gray text

Improve hierarchy through:

- deliberate font scale
- weight
- tracking
- line-height
- case
- contrast
- tabular figures for data
- stronger display treatment where appropriate

Typography should look designed, not merely formatted.

---

# 5. Color and Surfaces

Avoid default AI aesthetics.

Especially avoid:

- purple-to-blue gradients
- neon violet glow
- random cyan accents
- excessive glassmorphism
- glowing borders everywhere
- oversaturated accents
- multiple unrelated accent colors
- pure black backgrounds without nuance
- generic gray-on-gray SaaS palettes
- excessive shadow
- every element floating inside a bordered white card

Prefer:

- one dominant accent
- controlled neutral palette
- coherent warm or cool gray family
- subtle tonal separation
- restrained shadows
- carefully selected surface elevation
- subtle ambient gradients when useful
- texture or grain only when appropriate
- surfaces that communicate hierarchy

Not every section needs a container.

Not every container needs:

- a border
- a shadow
- a radius

Use surfaces deliberately.

---

# 6. Layout

Audit for generic patterns such as:

- sidebar + header + equal cards
- three identical cards in a row
- perfectly symmetrical layouts
- every module inside its own box
- excessive nested cards
- identical border radius everywhere
- content floating with no clear alignment system
- huge unused areas
- overly dense layouts
- excessive whitespace in data-heavy interfaces
- arbitrary gaps
- weak focal point
- primary action visually competing with secondary actions

Prefer deliberate composition.

Possible directions include:

- asymmetric dashboard
- editorial dashboard
- compact operational workspace
- top-navigation application
- contextual side rail
- command-center layout
- split pane
- master-detail
- bento layout used sparingly
- dense professional data workspace
- modular canvas
- visually integrated analytics
- sidebar with unconventional proportions
- horizontally structured workflow
- content-first layout
- full-width workspace with contextual controls

Choose a layout appropriate to the product.

Do not force every interface into a fashionable pattern.

---

# 7. Visual Hierarchy

The user should understand the page in roughly this order:

1. Where am I?
2. What is the current state?
3. What matters most?
4. What can I do?
5. What supporting information is available?

Create a clear hierarchy between:

- page-level information
- section-level information
- primary actions
- secondary actions
- status
- metadata
- tertiary controls

Avoid having ten elements with equal visual emphasis.

---

# 8. Component Redesign

Do not default to standard AI-generated component patterns.

## Cards

Avoid automatically using:

- white background
- 1px border
- 16px radius
- subtle shadow
- icon in colored square
- title
- description
- button

Consider whether the information even needs a card.

Alternative treatments:

- grouped surface
- section divider
- row
- timeline
- data strip
- segmented control
- table
- inline metric
- split panel
- expandable group
- contextual rail
- visual hierarchy using whitespace alone

## Buttons

Avoid giving every action equal weight.

Use clearly differentiated:

- primary
- secondary
- tertiary
- text
- icon
- destructive

actions.

Avoid excessive pill buttons.

## Badges

Do not turn every state into a colorful pill.

States may instead use:

- dot + text
- subtle tinted label
- icon
- plain semantic text
- small marker
- border treatment
- contextual color

## Navigation

Do not assume a left sidebar is mandatory.

Evaluate whether:

- top navigation
- compact sidebar
- icon rail
- contextual secondary navigation
- command palette
- tabs
- breadcrumbs

better serve the interface.

---

# 9. Avoid AI Slop

The result must not look like a generic AI-generated Dribbble dashboard.

Avoid:

- purple/blue gradient backgrounds
- excessive glass cards
- random glowing blobs
- floating geometric decorations
- gratuitous graphs
- fake charts added only for decoration
- excessive rounded rectangles
- icon inside colored rounded square for every feature
- excessive pills
- enormous radii
- gradients inside every CTA
- generic SaaS illustration style
- arbitrary 3-column feature cards
- fake futuristic styling
- gratuitous dark mode
- random decorative grids
- excessive shadow
- hero text taking half the viewport
- unnecessary floating cards
- meaningless numbers
- unreadable microtext

A professional interface should look plausible enough that a real software company could ship it.

---

# 10. Use Realistic Content

Preserve readable text from the reference whenever possible.

Do not replace meaningful content with:

- Lorem Ipsum
- random strings
- fake placeholder text
- nonsense labels
- generic "John Doe"
- meaningless metrics

When new content must be introduced, make it believable and consistent with the product.

Avoid AI-copy clichés such as:

- Elevate
- Seamless
- Unleash
- Next-Gen
- Revolutionary
- Game-changing
- Empower your journey
- Unlock the power of
- Transform your experience

Use concise product language.

---

# 11. Dashboard-Specific Rules

For dashboards and web applications:

Functionality takes priority over decoration.

The result should feel usable.

Make clear distinctions between:

- navigation
- controls
- content
- status
- metrics
- data
- actions

Keep data readable.

Do not reduce information density simply to make the interface look minimalist.

Professional dashboards can be dense.

The objective is **structured density**, not emptiness.

When appropriate, use:

- aligned numeric columns
- compact tables
- contextual filters
- sticky toolbars
- status indicators
- sparklines
- small charts
- grouped controls
- secondary rails
- progressive disclosure

Do not add analytics charts unless they make sense for the supplied product.

---

# 12. Landing Page-Specific Rules

For marketing pages:

Prioritize:

- narrative
- hierarchy
- product understanding
- visual rhythm
- differentiation
- trust
- conversion

Avoid the standard AI landing-page sequence:

Hero  
→ logo strip  
→ three feature cards  
→ bento grid  
→ testimonials  
→ three pricing cards  
→ FAQ accordion  
→ CTA

Vary page architecture according to the product.

Experiment with:

- editorial composition
- product screenshots
- oversized typography
- split narratives
- asymmetric grids
- sticky storytelling
- product demonstrations
- visual comparison
- contextual testimonials
- structured proof
- progressive feature storytelling

Do not add sections simply because SaaS landing pages normally contain them.

---

# 13. Redesign Strength

Default to a **meaningful redesign**, not a cosmetic refresh.

Unless the user asks to stay close to the original:

## Preserve

- product purpose
- important content
- functionality
- brand identity when visible and deliberate
- recognizable information
- page type

## Freely redesign

- layout
- spacing
- typography
- navigation presentation
- component presentation
- density
- grouping
- hierarchy
- visual language
- surfaces
- colors
- visual emphasis

A successful result should clearly come from the same product while looking substantially better.

---

# 14. Multiple Redesign Concepts

When the user requests multiple redesigns, every redesign must explore a **genuinely different design direction**.

However, multiple redesigns must **never be combined inside the same image**.

## Mandatory output rule

**ONE OUTPUT IMAGE = ONE REDESIGN.**

Each generated image must contain exactly one complete redesign of the requested interface.

If the user requests:

- 2 redesigns → generate 2 separate images
- 4 redesigns → generate 4 separate images
- 8 redesigns → generate 8 separate images

Each image must dedicate the full available canvas to a single concept.

Never interpret "generate 8 redesigns" as:

> create one image containing 8 redesign concepts.

Do not produce:

- contact sheets
- moodboards containing several redesigns
- grids of redesign alternatives
- side-by-side redesigns
- split-screen concept comparisons
- multiple browser windows showing different concepts
- before/after comparisons inside one image
- numbered concept boards
- 2×2, 3×3, 4×2, or similar concept grids
- thumbnail collections
- several miniature interfaces in the same output

Even when the model is capable of representing multiple concepts inside one image, **do not do so**.

Every concept must receive its own independent output image.

---

# 15. Making Multiple Outputs Genuinely Different

When producing several separate redesign images, do not generate:

- the same layout with different colors
- the same cards rearranged slightly
- eight variations of the same dashboard
- minor radius differences
- superficial typography swaps
- one concept repeatedly restyled

Instead vary major structural decisions.

For example, eight redesign images could independently explore:

1. compact enterprise workspace
2. editorial asymmetric interface
3. minimal top-navigation SaaS
4. dense command-center layout
5. modular canvas
6. master-detail application
7. contextual side-rail layout
8. highly minimal professional workspace

Each concept should differ in several of:

- global composition
- navigation
- hierarchy
- content grouping
- density
- component language
- typography
- surfaces
- visual rhythm

Color changes alone do not count as a separate concept.

Each concept must still respect the original product purpose and required functionality.

---

# 16. Full-Canvas Composition

Every output image should use the available canvas to properly present its single redesign.

The redesign should:

- occupy the canvas at an appropriate scale
- remain readable
- preserve realistic UI proportions
- show enough of the interface to understand the concept
- avoid unnecessary empty framing
- avoid artificially shrinking the interface

Do not shrink the redesign to leave space for:

- alternative concepts
- annotations
- titles
- labels such as "Concept A"
- explanatory diagrams
- comparison panels

Unless specifically requested, the image should simply present the redesigned interface itself.

The output should feel like a real screenshot of that design.

---

# 17. Image Fidelity

Generated interfaces must look like real software screenshots.

Aim for:

- crisp geometry
- correct alignment
- coherent perspective
- straight browser/UI edges
- consistent spacing
- consistent component dimensions
- realistic text placement
- realistic controls
- consistent iconography
- plausible data
- clean rendering

Avoid:

- distorted panels
- curved browser windows
- illegible text clouds
- duplicated UI
- warped icons
- random controls
- inconsistent button shapes
- misaligned tables
- impossible component geometry

The image should feel like a captured product interface, not concept art.

---

# 18. Maintain the Correct Viewport

Use the source screenshot to infer:

- desktop vs tablet vs mobile
- approximate aspect ratio
- expected information density
- visible viewport

Unless requested otherwise, keep the redesign in the same general device category.

Do not place the UI inside:

- laptop mockups
- phones
- floating browser windows
- 3D devices
- perspective scenes

unless explicitly requested.

Generate the interface itself.

---

# 19. Brand Handling

If the screenshot contains a recognizable brand system, first determine whether it should be preserved.

Usually preserve:

- logo
- product name
- distinctive brand color
- meaningful brand motifs

But improve the implementation when necessary.

Do not randomly rebrand an existing product unless the user asks for:

- new branding
- visual identity exploration
- completely different aesthetic directions

If the brand identity is weak or unspecified, you may establish a more coherent visual language.

---

# 20. Accessibility-Aware Visual Design

Even when generating static images, designs should visually suggest accessible implementation.

Maintain:

- sufficient contrast
- readable font size
- visible interactive affordances
- understandable states
- non-color-only status communication
- large enough controls
- clear hierarchy

Avoid light gray text with insufficient contrast simply because it looks minimal.

---

# 21. Use Decoration Sparingly

Decorative elements should strengthen the design.

They must not compensate for weak hierarchy.

Possible subtle enhancements:

- restrained texture
- faint grid
- soft ambient gradient
- contextual illustration
- product imagery
- subtle pattern
- controlled lighting
- architectural lines
- purposeful photography

Do not introduce decorative elements that compete with the actual interface.

---

# 22. Image Selection and Photography

If the original contains imagery:

Preserve its purpose but not necessarily the exact composition.

Prefer:

- authentic photography
- consistent art direction
- believable product imagery
- contextual imagery
- natural crops

Avoid uncanny stock imagery and generic AI people.

When redesigning food, architecture, products, equipment, or other recognizable real-world subjects, they should remain anatomically and physically plausible.

---

# 23. Iconography

Use one coherent icon family.

Avoid:

- mixed stroke widths
- mixed filled/outline styles
- generic icon clichés everywhere
- decorative icons that communicate nothing

Icons should improve scanning.

They should not exist merely to fill empty space.

---

# 24. Optical Alignment

Do not rely solely on mathematical alignment.

Apply optical adjustments where appropriate to:

- icon + label combinations
- centered buttons
- circular controls
- badges
- logos
- numeric values
- typography

Professional UI often requires small visual corrections.

---

# 25. Restraint

A redesign does not need to demonstrate every contemporary UI technique simultaneously.

Do not combine all of the following without reason:

- glassmorphism
- gradients
- grain
- bento
- glow
- floating cards
- oversized typography
- pill navigation
- blurred backgrounds
- 3D illustrations

Choose a visual system and commit to it.

Consistency is more valuable than spectacle.

---

# 26. Decision Priority

When redesigning, make decisions in this order:

1. Understand product purpose
2. Identify critical information
3. Establish information hierarchy
4. Choose global layout
5. Determine density
6. Establish typography
7. Establish palette
8. Define component language
9. Refine spacing
10. Add supporting visual details
11. Remove unnecessary decoration
12. Perform final coherence pass

Do not begin by changing colors.

---

# 27. Final Coherence Pass

Before producing each final image, mentally audit it.

Ask:

## Product

- Is the purpose of the page still obvious?
- Are important capabilities preserved?
- Can the user understand what actions are possible?

## Layout

- Is there a strong focal point?
- Is information grouped logically?
- Is whitespace intentional?
- Are alignments coherent?

## Visual language

- Is there one clear design system?
- Are radii consistent but not monotonous?
- Are surfaces intentional?
- Is the accent color controlled?

## Typography

- Is there clear hierarchy?
- Are labels readable?
- Do numbers align properly?
- Is unnecessary bolding removed?

## Components

- Are there too many cards?
- Are there too many pills?
- Are buttons properly prioritized?
- Is every container necessary?

## AI fingerprint

- Does this look like a generic AI dashboard?
- Are there unnecessary gradients?
- Are there arbitrary floating cards?
- Is the composition suspiciously symmetrical?
- Is decorative styling replacing product design?

## Output composition

- Does this image contain exactly one redesign?
- Is the redesign using the canvas properly?
- Did any secondary redesign, thumbnail, comparison, or alternative accidentally appear?
- Is the interface shown at a useful and readable scale?

If more than one redesign appears in the image, the output is invalid and must be recomposed with only one redesign.

---

# 28. Hard Rules

- **Every output image must contain exactly ONE redesign.**
- **Never place multiple redesign concepts in a single image.**
- **If multiple redesigns are requested, generate them as separate output images.**
- **Use the full canvas for each individual redesign.**
- **Never create contact sheets, concept grids, moodboards, or side-by-side redesign comparisons unless the user explicitly requests that exact format.**
- Do not merely recolor the provided screenshot.
- Do not preserve a weak layout simply because it exists in the reference.
- Do not remove essential product functionality for aesthetic reasons.
- Do not invent major unrelated functionality unless requested.
- Do not add decorative charts without a functional reason.
- Do not use gibberish text when readable UI text can be produced.
- Do not create gratuitous futuristic visuals.
- Do not use purple-blue AI gradients by default.
- Do not put every piece of information inside a card.
- Do not overuse rounded pills.
- Do not treat minimalism as removing useful information.
- Do not confuse decoration with hierarchy.
- Do not put the interface inside device mockups unless requested.
- Do not make all redesign variants structurally identical.
- Do not output a slightly modified clone when the user requested a complete redesign.
- Do not change logos, product names, or core brand identity unless requested.
- Do not make interfaces less usable simply to make them more visually dramatic.

---

# 29. User Intent Overrides

Always follow the requested redesign intensity.

Examples:

## "Improve this"

Stay relatively close to the original structure while upgrading visual quality.

## "Redesign this"

Meaningfully reconsider layout, hierarchy, typography, components, and visual style.

## "Complete redesign"

Treat the current screenshot primarily as functional and informational input. Freely rebuild the visual composition.

## "Explore different directions"

Produce substantially different concepts, with **one separate output image per concept**.

## "Create 8 redesigns"

Produce **8 separate output images**, each containing one full redesign.

Never create one image containing all eight.

## "Don't change the layout"

Preserve composition and focus on visual styling.

## "Don't change anything except X"

Edit only the specified element.

The user's explicit constraints always override the default redesign freedom.

---

# 30. Default Generation Objective

When no narrower direction is provided, generate a redesign that feels:

- professional
- intentional
- contemporary
- product-led
- visually coherent
- realistic
- premium without being flashy
- distinctive without being experimental for its own sake
- cleaner than the original
- easier to scan
- plausibly shippable by a real product team

The end result should not merely be prettier.

It should communicate the product more effectively.

And regardless of how many concepts are requested:

**one image must always represent one redesign and one redesign only.**
