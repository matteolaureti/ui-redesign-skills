# Dashboard Redesign

## Job to be done

Turn an existing dashboard screenshot into a more usable, coherent and credible operational interface.

Treat a dashboard as a **workspace**, not as a marketing page.

The goal is not maximum minimalism. The goal is **structured density**.

## Mandatory output rule

**ONE OUTPUT IMAGE = ONE DASHBOARD REDESIGN.**

If several dashboard concepts are requested, generate separate images.

Never create a dashboard contact sheet, grid of alternatives or side-by-side concept board unless explicitly requested.

## Inputs to inspect

Identify:

- who is operating the dashboard;
- what they need to monitor;
- what they need to act on;
- which information is global;
- which information belongs to a selected entity;
- which data is historical;
- which data is real-time or status-based;
- which controls are filters versus actions.

## Workflow

### 1. Classify dashboard type

Examples:

- executive overview;
- operational control center;
- analytics;
- account management;
- device/fleet management;
- CRM;
- content operations;
- billing;
- moderation;
- monitoring;
- admin/backoffice.

Match density and hierarchy to the job.

### 2. Establish the operating hierarchy

Prioritize:

1. current state;
2. anomalies / items requiring attention;
3. primary actions;
4. key metrics;
5. trends;
6. recent activity;
7. secondary metadata.

Do not automatically place four KPI cards at the top.

### 3. Decide navigation architecture

Evaluate whether the product benefits from:

- standard sidebar;
- compact sidebar;
- icon rail;
- top navigation;
- section tabs;
- contextual secondary rail;
- master-detail navigation.

A left sidebar is not mandatory.

### 4. Treat metrics deliberately

A metric deserves high prominence when it changes decisions.

Avoid:

- a grid of equal KPI cards simply because metrics exist;
- meaningless percentage deltas;
- oversized numbers for low-value information.

Alternatives:

- integrated summary header;
- horizontal data strip;
- compact metric row;
- contextual values attached to charts or entities;
- grouped operational summary.

### 5. Choose tables when tables are the right tool

Do not convert structured datasets into cards just to look modern.

For multi-record operational data, favor:

- readable columns;
- consistent alignment;
- clear row actions;
- sensible density;
- filters near the table;
- selected/hover state cues;
- sticky regions when conceptually useful.

Numbers should visually align.

### 6. Design filters as a system

Distinguish:

- global filters;
- local module filters;
- search;
- sort;
- time range;
- saved view;
- entity selection.

Do not scatter filter pills everywhere.

Make active constraints understandable.

### 7. Make status scannable

Use restrained semantic treatment.

Possible patterns:

- dot + label;
- icon + text;
- subtle tint;
- compact status cell;
- edge marker.

Avoid turning every state into a large rounded badge.

Critical anomalies should be more prominent than ordinary healthy states.

### 8. Place actions where they act

Prefer contextual actions near affected content.

Do not place every possible action in the page header.

Differentiate:

- primary page action;
- entity-level action;
- row action;
- destructive action;
- overflow action.

### 9. Handle activity and anomalies

Recent activity, alerts and anomalies are often better in:

- a contextual side rail;
- a focused feed;
- an attention queue;
- a timeline;
- a compact status region.

Do not let them compete equally with the main task.

### 10. Use charts only when they answer a question

Every chart should support an actual decision or trend.

Avoid decorative analytics.

Do not add charts that are absent from the product's meaning merely to make the dashboard look sophisticated.

### 11. Preserve power-user efficiency

A polished dashboard can be visually dense.

Avoid excessive whitespace that forces unnecessary scrolling.

Optimize for:

- fast scanning;
- predictable placement;
- clear grouping;
- repeat usage;
- useful visible information.

## Useful design directions

Depending on the product, consider:

- compact enterprise workspace;
- command center;
- master-detail interface;
- contextual side rail;
- full-width operational table;
- modular canvas;
- top-navigation workspace;
- asymmetrical overview;
- entity-centric dashboard.

Do not choose a direction because it is fashionable. Choose it because it supports the task.

## Common failure modes

Reject concepts that:

- are mostly empty;
- use giant typography instead of information;
- contain a generic 4-card KPI row;
- put every module inside an identical card;
- add random line charts;
- use dozens of colored status pills;
- bury the primary operational action;
- make tables harder to read;
- look like a landing page;
- look like a Dribbble dashboard rather than a tool used all day.

## Final checks

- Is the primary operational state obvious?
- Can anomalies be found quickly?
- Are important actions near their context?
- Is the information density appropriate?
- Are tables/lists easier to scan?
- Are metrics prioritized by usefulness?
- Is navigation proportional to the product?
- Does the screenshot look like realistic software?
- Does the output contain exactly one redesign?
