# Landing Page Redesign

## Job to be done

Rebuild an existing landing page into a stronger marketing experience that explains the product clearly and creates a deliberate conversion path.

A landing page is not just a collection of attractive sections.

It is a narrative.

## Mandatory output rule

**ONE OUTPUT IMAGE = ONE LANDING-PAGE REDESIGN.**

When multiple concepts are requested, generate separate images.

Never place several full landing-page concepts into one canvas unless the user explicitly asks for a comparison board.

## Workflow

### 1. Understand the offer

Identify:

- product;
- target user;
- problem;
- value proposition;
- primary CTA;
- secondary CTA;
- trust signals;
- product proof;
- pricing relevance.

Do not redesign the page before understanding what it is selling.

### 2. Find the narrative

A strong page should answer progressively:

1. What is this?
2. Why should I care?
3. How does it work?
4. Can I trust it?
5. Is it right for me?
6. What should I do next?

Not every page needs to answer these through identical sections.

### 3. Rebuild the hero when necessary

The hero should establish:

- product category;
- specific value;
- visual evidence;
- primary action.

Avoid:

- vague oversized slogans;
- generic gradient backgrounds;
- detached floating dashboard cards;
- generic “Get started / Learn more” dual-button pattern without reason;
- decorative product mockups that do not explain anything.

Use product UI, photography, diagrams or copy according to the product.

### 4. Avoid the default AI SaaS sequence

Do not automatically produce:

Hero
→ logo strip
→ 3 feature cards
→ bento grid
→ testimonials
→ 3 pricing towers
→ FAQ accordion
→ CTA.

That sequence is allowed only when it genuinely serves the product.

Consider:

- editorial storytelling;
- split product demonstrations;
- sticky product narrative;
- asymmetric feature chapters;
- before/after explanation;
- problem/solution proof;
- visual workflows;
- comparison;
- use-case stories;
- integrated social proof;
- progressive pricing explanation.

### 5. Treat product visuals as evidence

Screenshots and product imagery should show:

- actual capability;
- an important workflow;
- a meaningful result.

Do not use interface imagery merely as decoration.

### 6. Create section rhythm

Vary:

- text-to-visual balance;
- section depth;
- alignment;
- content density;
- image scale;
- whitespace.

Avoid a page where every section is:
heading + paragraph + three cards.

### 7. Use social proof deliberately

Possible proof:

- logos;
- quantified results;
- testimonials;
- case-study fragments;
- recognizable workflows;
- certifications;
- customer counts;
- product evidence.

Do not add invented proof when the source does not support it.

### 8. Redesign pricing as a decision interface

If pricing is present, optimize comparison.

Avoid three identical towers with one slightly taller.

Clarify:

- who each plan is for;
- meaningful differences;
- recommended option;
- billing cadence;
- limits;
- CTA hierarchy.

### 9. Treat FAQs as information design

An accordion is not mandatory.

Alternatives:

- categorized help;
- two-column Q&A;
- progressive disclosure;
- pricing-specific questions;
- inline objection handling;
- searchable help pattern.

### 10. Maintain brand coherence

Use brand elements intentionally across:

- typography;
- palette;
- imagery;
- UI screenshots;
- iconography;
- copy tone.

Do not substitute generic AI aesthetics for the brand.

## Common failure modes

Reject concepts that:

- use purple-blue gradients by default;
- look like every AI-generated SaaS website;
- contain a hero that says little about the product;
- overuse bento cards;
- use meaningless abstract 3D art;
- make the page long without advancing the story;
- introduce fake logos or testimonials;
- repeat the same layout section after section;
- make every CTA equally prominent.

## Final checks

- Is the product understandable above the fold?
- Is the value proposition specific?
- Does each section advance the story?
- Are product visuals informative?
- Are trust and proof believable?
- Is CTA hierarchy clear?
- Does the page avoid generic AI SaaS composition?
- Does the output contain exactly one redesign?
